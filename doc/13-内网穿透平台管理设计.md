# 13 · 内网穿透平台管理（NATFRP / ChmlFrp 双平台对接）

> 状态：已实现（migration v10）。真机联调已覆盖两个平台的鉴权、隧道、节点、
> 配置下载与用量接口；E2E 见 §11。

## 1. 背景与核心洞察

面板已有的 WG 组网解决的是「自建机器之间互通」，但不少场景（家宽无公网 IP、
临时对外暴露一个服务）走的是第三方穿透平台。本项目对接国内两家：

- **NATFRP（樱花内网穿透）** —— 开放 API v4，用「访问密钥」直连；
- **ChmlFrp** —— v2 API，鉴权走轻爪账户 OAuth2。

对接前先把两件事摸清楚，它们直接决定了模块能做到什么程度：

**（1）两平台的鉴权模型完全不同，不能用同一套凭据抽象。**

| | NATFRP | ChmlFrp |
| --- | --- | --- |
| 凭据 | 访问密钥（面板生成） | OAuth2 access_token + refresh_token |
| 有效期 | **长期有效**，手动重置才失效 | access_token **600 秒**，靠 refresh_token 续期 |
| 获取方式 | 用户粘贴 | 必须走设备码/授权码交互，无法由用户名密码换取 |
| 请求头 | `Authorization: Bearer <密钥>` | 同上 |

> ChmlFrp 的账号密码登录端点**已下线**（`POST /login` 现在返回「缺少 access_token 参数」），
> 官方启动器源码里的密码登录代码是滞后的。它的面板 SSO 流程 `return_url` 被服务端
> **硬编码**到 `panel.chmlfrp.net`（实测传入自定义 return_url 无效），因此也抓不到回调令牌。
> **结论：设备码（RFC 8628）是唯一可行的 headless 接入路径。**

**（2）refresh_token 是一次性的，刷新即轮换。**

实测：用 refresh_token 换到新 access_token 后，**旧的 access_token 立即失效**，
refresh_token 本身也换成了新的。没有立刻持久化新值 = 整条链路断掉，
且只能引导用户重新授权。这带来三条硬约束，见 §5。

### 能力边界（先明确做不到的）

| 需求 | NATFRP | ChmlFrp | 说明 |
| --- | --- | --- | --- |
| 启动隧道 | ❌ | ❌ | 两家都只能「下发配置 + 本地跑 frpc」，API 无启动入口 |
| 停止隧道 | ❌ | ⚠️ 仅强制下线 | ChmlFrp `/offline_tunnel` 只能踢掉当前连接 |
| 签到 | ❌ | ❌ | 均强制图形验证码（GeeTest），无法程序化 |
| 连接数 | ❌ | ✅ `cur_conns` | NATFRP 只有 `online` 布尔 |
| DNS 写操作 | ❌ 只读 | ✅ 二级域名增删改 | |
| Webhook | ❌ | ❌ | 官网宣传有，实际无任何端点 |

因此本模块的定位是**监控 + 配置管理**，不是「隧道开关」。UI 上不提供启停按钮，
避免给出无效预期。

## 2. 范围与边界

**做**：账号绑定/解绑、用量看板、隧道全生命周期（增删改查 + 配置下载 + 锁定/迁移/
认证/下线）、节点列表与负载、用量趋势、ChmlFrp 免费二级域名管理、每 2 分钟自动同步。

**不做**：启停隧道、签到、代跑 frpc、DNS（NATFRP 侧只读）。

## 3. 后端架构

```
internal/frp/
  client.go    归一化类型（Account/Tunnel/Node/TrafficPoint）+ HTTP 骨架 + ErrAuth/ErrUnsupported
  natfrp.go    NATFRP 客户端（OpenAPI v4）
  chmlfrp.go   ChmlFrp 客户端（v2）
  oauth.go     轻爪账户 OAuth2 设备码流程 + 令牌刷新
  runner.go    协调层：凭据解密、令牌续期、同步落库、写操作分派
```

`handler/frp.go` 只做参数校验、错误码翻译与视图拼装，不直接碰 HTTP 客户端；
`internal/tasks` 每 2 分钟调一次 `Runner.SyncAll`。

### 3.1 两个平台的协议坑（都是真机联调才发现的）

写客户端时按官方文档实现会踩到下面这些，全部已在代码与单测中固化：

1. **NATFRP 错误统一返回 HTTP 500**，真实错误码在 body 的 `code` 字段。
   只看 HTTP 状态码会把「访问密钥无效」当成服务端故障。
2. **NATFRP 前置 Cloudflare 会拦默认脚本 UA**（Python-urllib 直接 403 `error code: 1010`），
   必须显式设置 User-Agent。
3. **NATFRP 节点 flag 的低两位是独立能力位，不是掩码。**
   规范写 `0b11: 允许 HTTP 隧道`，若理解为「两位都置位才算支持」，
   实测全网 71 个节点里 `flag&0b11` 只取 0/1/2、**从不出现 3**，
   会导致「没有任何节点支持建站」的荒谬结论。正确语义：bit0=HTTP、bit1=HTTPS。
4. **ChmlFrp 把布尔语义字段序列化成字符串**：`"encryption":"false"`、`"state":"true"`。
   声明成 Go `bool` 会让整个列表解码失败。
5. **ChmlFrp 的 `uptime` 是 ISO 时刻而非秒数**（与 NATFRP 语义相反，需换算成时长）。
6. **ChmlFrp 的 `tunnel` 是上限、`tunnelCount` 是已用**，与官方文档说明相反
   （实测 `tunnel=4 / tunnelCount=1`，而账号下确实只有 1 条隧道，免费用户默认 4 条）。
7. **ChmlFrp 业务错误几乎都返回 HTTP 200**，结果在 JSON 的 `code` 里。
8. **ChmlFrp 文档滞后**：`/node_status_info` 的参数实际是 `nodename` 而非文档写的 `node`；
   `/delete_tunnel` 文档标注「开发中」但线上已可用（面板自己就在用）。

## 4. 数据模型（migration v10）

| 表 | 用途 | 关键点 |
| --- | --- | --- |
| `frp_platform` | 平台账号 + 凭据 + 最新画像 | `token_enc`/`refresh_enc` 为 AES-256-GCM 密文；`(kind,name)` 唯一 |
| `frp_tunnel` | 隧道镜像 | `(platform_id, remote_id)` 唯一，同步时 upsert + 删除平台侧已消失的行 |
| `frp_node` | 节点镜像 | 整表替换语义，节点集合变动慢 |
| `frp_usage` | 用量快照 | 面板自留，用于画跨平台统一趋势（平台侧历史接口粒度不一） |

- 凭据列一律 `BLOB` + `json:"-"`，接口只下发 `has_token`；
- `frp_usage` 同分钟内重复同步只保留最后一条（手动连点不会把趋势图打散）；
- `frp_usage` 保留 30 天，由 10 分钟清理任务 `PruneFRPUsage` 回收。

## 5. 令牌生命周期（本模块最容易出事的地方）

`Runner` 用**每个平台一把互斥锁**串行化「同步 + 续期 + 写操作」，原因是：

1. **refresh_token 一次性**：两个 goroutine 同时刷新，一个成功一个拿到 `invalid_grant`，
   失败方的落库还可能覆盖成功方的新令牌 → 链路直接断；
2. 续期与业务调用必须原子：拿到新令牌后要**立刻** `UpdateFRPPlatformCreds` 落库，
   否则进程重启/并发请求仍在用已失效的旧令牌。

刷新时机：`TokenExpireAt - now < 90s`（留一次请求往返的余量）。
刷新失败（`invalid_grant`）→ 平台状态降级为 `unbound`，前端据此弹「重新授权」。

**重新授权保留数据**：`FRPChmlfrpDeviceStart` 接受 `reuse_id`，重新授权时只换凭据，
隧道镜像与用量历史不动。

**公共客户端说明**：设备码需要一个开启 device flow 的 `client_id`。
默认用 ChmlFrp 官方启动器的公共客户端（无 secret，实测可用），可通过
`BEACON_CHMLFRP_CLIENT_ID` 换成自己在 `account.qzhua.net/console` 申请的客户端
（需勾选 `chmlfrp_api` scope）。该默认值不属于本项目，平台方若回收需自行替换。

| GET | `/frp/nodes` | 跨平台节点列表 |

| GET | `/frp/tunnels/:id/traffic` | 单隧道流量曲线 |
| POST/GET/DELETE | `/frp/chmlfrp/device[/:sid]` | 设备码授权：发起 / 轮询 / 取消 |

错误码（doc/04 的 2020 段）：

| code | 含义 |
| --- | --- |
| 2020 | 该平台不支持此操作（如对 ChmlFrp 调锁定） |
| 2021 | 平台凭据失效，需重新授权 |
| 2022 | 上游平台调用失败 |

**约定**：
- 凭据只进不出，接口永不回显密钥；
- 平台能力不等价的操作**明确拒绝**（2020）而不是静默失败；
- `DELETE /subdomains` 用查询参数传 `domain`/`record`（DELETE 带 body 在部分代理上不可靠）；
- 所有外部调用带 30–45s 超时，前端 `retries: 0`（重试会重复建隧道）。

## 7. 同步策略

- **周期**：`tasks` 每 2 分钟一次轻同步（账号 + 隧道），不拉节点列表（节点变动慢，省两次外部请求）；
  轻同步每平台仅 2 个上游请求，2 分钟对上游是零感知频率（性能审查 2026-09：3min→2min）。
- **手动同步**：`?full=1` 连节点一起拉；每平台一把锁，与周期任务串行。
- **失败不覆盖**：任一环节失败只写 `last_error` + 降级状态，**保留上次成功的镜像**，
  平台临时抖动时面板仍能展示有效数据。
- **写操作后立即轻同步**：新建/删除隧道后马上回读，避免用户手动刷新。

## 8. 前端（/admin/frp，懒加载 chunk ~11.7KB gzip）

页面结构（v2.1 归一化改版）：

1. **平台卡**（纯展示，不切换下方内容）：平台名 + 状态标签 + 四格特色指标
   （隧道在线/配额、剩余流量或累计上传、签到或累计下载）+ 行内操作（同步/换密钥或重新授权/解绑）；
   用户名等账号画像不出现在卡片标题。
2. **账号用量**：跨平台归一化的键值瓦片，每平台一块（今日流量 / 剩余流量或累计上传下载 / 限速 / 上次同步）。
3. **流量历史**：一张图两条曲线（NATFRP 蓝、ChmlFrp 紫），day 口径同为 7 点天然对齐。
4. **隧道**：跨平台合并表，`平台` 列标注归属；操作列按平台能力渲染
   （NATFRP：编辑/配置/锁定/迁移/认证/删除；ChmlFrp：编辑/配置/下线/删除）。
   「新建隧道」弹窗顶部选平台，节点候选跟随所选平台的镜像。
5. **在用节点**：合并表（`平台` 列标注归属），只列被隧道挂载的节点；
   「未在用节点（N）」默认折叠（虚线描边手风琴），建隧道/迁移在弹窗下拉中选节点，不依赖这张全量表。
6. **免费二级域名**：ChmlFrp 特有区块独立成卡（后端接口按平台挂载）。

弹窗：绑定 NATFRP、设备码授权、建/改隧道（含平台选择）、迁移、锁定、解析、危险确认。

- 视图只读 store、只调 actions，不直连 API 门面（doc/10）；
- store 的 `frpDetails` 按平台 id 存详情（双平台同屏，不再是单选模型），
  写操作后只刷新对应平台那份；
- 设备码授权弹窗按 3 秒轮询后端（后端已按平台 `interval` 节流，前端多问不会多打上游）；
- 配置下载走裸 `fetch` + blob（doc/10 §8 明示的唯一下载例外），`revokeObjectURL` 已调用；
- 状态一律「颜色 + 文字」双通道；破坏性操作走 `ConfirmDialog`。

## 9. 安全

- 凭据 AES-256-GCM 加密落库（复用 `internal/crypto`，与 SSH 凭据同一主密钥）；
- 接口层只下发 `has_token`，`store.FRPPlatform.TokenEnc/RefreshEnc` 标 `json:"-"`；
- **ChmlFrp 的 `/nodeinfo` 会返回节点级 `apitoken`/`nodetoken`**，本模块**不调用该端点**；
  联调脚本里对该字段做了打码，避免进入日志；
- 平台返回的 `auth.token`（frpc 配置内）只在用户主动点「配置」时以附件下发，不落库；
- 下载文件名经 `sanitizeFileName` 白名单过滤（隧道名可能含任意字符）；
- 所有写操作进审计日志（`frp_platform_bind`、`frp_tunnel_create` 等）。

## 12. 游客面板暴露面（/tunnels，v2.1 新增）

管理端看全量，游客端只看「用得多不多、通不通」。公开页多一个入口就必须多问一次
「这条数据是平台的公开信息，还是我的账号信息」——本模块的答案是后者一律不下发。

### 12.1 接口与字段白名单

`GET /api/v1/public/frp`（无鉴权；`private_mode=true` 且未登录时 401/1002），
响应体就是白名单，详见 [doc/04 §1.5](./04-API接口设计.md)：

| 下发 | 不下发 |
| --- | --- |
| 平台展示名、`kind`、同步是否正常 | 用户名 / UID / 实名 / 账号分组 |
| 隧道总数 / 在线数 / 连接数 | 剩余流量、限速（套餐与资费信息） |
| 今日流量消耗（两平台各自口径归一） | 节点域名 `host`、节点 `remote_id` |
| **在用**节点的名称、分组、在线、负载、在线时长 | 隧道名、本地/内网端点、公网端点 |
| 上次同步时间 | 平台的错误原文（`last_error`） |

### 12.2 节点只给「在用的」

平台节点表是全网节点（NATFRP 实测 71 条、ChmlFrp 39 条），对访客既无信息量又等于公开
未使用的拓扑。`store.ListFRPNodesInUse` 按「隧道记录里的 `node_id` = 节点 `remote_id`」关联，
只回被本账号隧道挂载的节点；管理端保留全网列表但标记 `in_use`，并在 UI 上
「在用展开 / 未在用折叠」。注意 ChmlFrp 的 `/tunnel` 只返回节点名不返回节点 ID，
`runner.fillNodeNames` 会按名称反查节点镜像补齐 `node_id`（首次同步若节点镜像尚未
落库，下一轮 full 同步补上）——漏了这一步 ChmlFrp 的 in_use 永远匹配不到。

### 12.3 前端

`views/monitor/TunnelView.vue`（路由 `/tunnels`，懒加载 2.6KB gzip，不进公开首屏）：
KPI 条（今日流量 / 在线隧道 / 在用节点 / 连接数）+ 每平台一张玻璃卡（用量三栏 + 在用节点列表 + 负载条）。
数据源是 `stores/monitor.js` 的 `startFrp/stopFrp`——**独立 60 秒低频轮询**，
挂载时启动、离开页面即清定时器（后台每 2 分钟才同步一次平台，跟着 10 秒主轮询纯属浪费）。
