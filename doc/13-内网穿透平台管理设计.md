# 13 · 内网穿透平台管理（NATFRP / ChmlFrp 双平台对接）

> 状态：已实现（migration v10）。真机联调已覆盖两个平台的鉴权、隧道、节点、
> 配置下载与用量接口；E2E 见 §11。

## 1. 背景与核心洞察

面板已有的 WG 组网解决的是「自建机器之间互通」，但不少场景（家宽无公网 IP、
临时对外暴露一个服务）走的是第三方穿透平台。本项目对接国内两家：

- **NATFRP（樱花内网穿透）** —— 开放 API v4，用「访问密钥」直连；
- **ChmlFrp** —— v2 API，鉴权走轻爪账户 OAuth2。

对接前先把两件事摸清楚，它们直接决定了模块能做到什么程度：

**（1）两平台的鉴权模型完全不同，不能用同一套凭据抽象。**

| | NATFRP | ChmlFrp |
| --- | --- | --- |
| 凭据 | 访问密钥（面板生成） | OAuth2 access_token + refresh_token |
| 有效期 | **长期有效**，手动重置才失效 | access_token **600 秒**，靠 refresh_token 续期 |
| 获取方式 | 用户粘贴 | 必须走设备码/授权码交互，无法由用户名密码换取 |
| 请求头 | `Authorization: Bearer <密钥>` | 同上 |

> ChmlFrp 的账号密码登录端点**已下线**（`POST /login` 现在返回「缺少 access_token 参数」），
> 官方启动器源码里的密码登录代码是滞后的。它的面板 SSO 流程 `return_url` 被服务端
> **硬编码**到 `panel.chmlfrp.net`（实测传入自定义 return_url 无效），因此也抓不到回调令牌。
> **结论：设备码（RFC 8628）是唯一可行的 headless 接入路径。**

**（2）refresh_token 是一次性的，刷新即轮换。**

实测：用 refresh_token 换到新 access_token 后，**旧的 access_token 立即失效**，
refresh_token 本身也换成了新的。没有立刻持久化新值 = 整条链路断掉，
且只能引导用户重新授权。这带来三条硬约束，见 §5。

### 能力边界（先明确做不到的）

| 需求 | NATFRP | ChmlFrp | 说明 |
| --- | --- | --- | --- |
| 启动隧道 | ❌ | ❌ | 两家都只能「下发配置 + 本地跑 frpc」，API 无启动入口 |
| 停止隧道 | ❌ | ⚠️ 仅强制下线 | ChmlFrp `/offline_tunnel` 只能踢掉当前连接 |
| 签到 | ❌ | ❌ | 均强制图形验证码（GeeTest），无法程序化 |
| 连接数 | ❌ | ✅ `cur_conns` | NATFRP 只有 `online` 布尔 |
| DNS 写操作 | ❌ 只读 | ✅ 二级域名增删改 | |
| Webhook | ❌ | ❌ | 官网宣传有，实际无任何端点 |

因此本模块的定位是**监控 + 配置管理**，不是「隧道开关」。UI 上不提供启停按钮，
避免给出无效预期。

## 2. 范围与边界

**做**：账号绑定/解绑、用量看板、隧道全生命周期（增删改查 + 配置下载 + 锁定/迁移/
认证/下线）、节点列表与负载、用量趋势、ChmlFrp 免费二级域名管理、每 2 分钟自动同步。

**不做**：启停隧道、签到、代跑 frpc、DNS（NATFRP 侧只读）。

## 3. 后端架构

```
internal/frp/
  client.go    归一化类型（Account/Tunnel/Node/TrafficPoint）+ HTTP 骨架 + ErrAuth/ErrUnsupported
  natfrp.go    NATFRP 客户端（OpenAPI v4）
  chmlfrp.go   ChmlFrp 客户端（v2）
  oauth.go     轻爪账户 OAuth2 设备码流程 + 令牌刷新
  runner.go    协调层：凭据解密、令牌续期、同步落库、写操作分派
```

`handler/frp.go` 只做参数校验、错误码翻译与视图拼装，不直接碰 HTTP 客户端；
`internal/tasks` 每 2 分钟调一次 `Runner.SyncAll`。

### 3.1 两个平台的协议坑（都是真机联调才发现的）

写客户端时按官方文档实现会踩到下面这些，全部已在代码与单测中固化：

1. **NATFRP 错误统一返回 HTTP 500**，真实错误码在 body 的 `code` 字段。
   只看 HTTP 状态码会把「访问密钥无效」当成服务端故障。
2. **NATFRP 前置 Cloudflare 会拦默认脚本 UA**（Python-urllib 直接 403 `error code: 1010`），
   必须显式设置 User-Agent。
3. **NATFRP 节点 flag 的低两位是独立能力位，不是掩码。**
   规范写 `0b11: 允许 HTTP 隧道`，若理解为「两位都置位才算支持」，
   实测全网 71 个节点里 `flag&0b11` 只取 0/1/2、**从不出现 3**，
   会导致「没有任何节点支持建站」的荒谬结论。正确语义：bit0=HTTP、bit1=HTTPS。
4. **ChmlFrp 把布尔语义字段序列化成字符串**：`"encryption":"false"`、`"state":"true"`。
   声明成 Go `bool` 会让整个列表解码失败。
5. **ChmlFrp 的 `uptime` 是 ISO 时刻而非秒数**（与 NATFRP 语义相反，需换算成时长）。
6. **ChmlFrp 的 `tunnel` 是上限、`tunnelCount` 是已用**，与官方文档说明相反
   （实测 `tunnel=4 / tunnelCount=1`，而账号下确实只有 1 条隧道，免费用户默认 4 条）。
7. **ChmlFrp 业务错误几乎都返回 HTTP 200**，结果在 JSON 的 `code` 里。
8. **ChmlFrp 文档滞后**：`/node_status_info` 的参数实际是 `nodename` 而非文档写的 `node`；
   `/delete_tunnel` 文档标注「开发中」但线上已可用（面板自己就在用）。

## 4. 数据模型（migration v10）

| 表 | 用途 | 关键点 |
| --- | --- | --- |
| `frp_platform` | 平台账号 + 凭据 + 最新画像 | `token_enc`/`refresh_enc` 为 AES-256-GCM 密文；`(kind,name)` 唯一 |
| `frp_tunnel` | 隧道镜像 | `(platform_id, remote_id)` 唯一，同步时 upsert + 删除平台侧已消失的行 |
| `frp_node` | 节点镜像 | 整表替换语义，节点集合变动慢 |
| `frp_usage` | 用量快照 | 面板自留，用于画跨平台统一趋势（平台侧历史接口粒度不一） |

- 凭据列一律 `BLOB` + `json:"-"`，接口只下发 `has_token`；
- `frp_usage` 同分钟内重复同步只保留最后一条（手动连点不会把趋势图打散）；
- `frp_usage` 保留 30 天，由 10 分钟清理任务 `PruneFRPUsage` 回收。

## 5. 令牌生命周期（本模块最容易出事的地方）

`Runner` 用**每个平台一把互斥锁**串行化「同步 + 续期 + 写操作」，原因是：

1. **refresh_token 一次性**：两个 goroutine 同时刷新，一个成功一个拿到 `invalid_grant`，
   失败方的落库还可能覆盖成功方的新令牌 → 链路直接断；
2. 续期与业务调用必须原子：拿到新令牌后要**立刻** `UpdateFRPPlatformCreds` 落库，
   否则进程重启/并发请求仍在用已失效的旧令牌。

刷新时机：`TokenExpireAt - now < 90s`（留一次请求往返的余量）。
刷新失败（`invalid_grant`）→ 平台状态降级为 `unbound`，前端据此弹「重新授权」。

**重新授权保留数据**：`FRPChmlfrpDeviceStart` 接受 `reuse_id`，重新授权时只换凭据，
隧道镜像与用量历史不动。

**公共客户端说明**：设备码需要一个开启 device flow 的 `client_id`。
默认用 ChmlFrp 官方启动器的公共客户端（无 secret，实测可用），可通过
`BEACON_CHMLFRP_CLIENT_ID` 换成自己在 `account.qzhua.net/console` 申请的客户端
（需勾选 `chmlfrp_api` scope）。该默认值不属于本项目，平台方若回收需自行替换。

| GET | `/frp/nodes` | 跨平台节点列表 |

| GET | `/frp/tunnels/:id/traffic` | 单隧道流量曲线 |
| POST/GET/DELETE | `/frp/chmlfrp/device[/:sid]` | 设备码授权：发起 / 轮询 / 取消 |

错误码（doc/04 的 2020 段）：

| code | 含义 |
| --- | --- |
| 2020 | 该平台不支持此操作（如对 ChmlFrp 调锁定） |
| 2021 | 平台凭据失效，需重新授权 |
| 2022 | 上游平台调用失败 |

**约定**：
- 凭据只进不出，接口永不回显密钥；
- 平台能力不等价的操作**明确拒绝**（2020）而不是静默失败；
- `DELETE /subdomains` 用查询参数传 `domain`/`record`（DELETE 带 body 在部分代理上不可靠）；
- 所有外部调用带 30–45s 超时，前端 `retries: 0`（重试会重复建隧道）。

## 7. 同步策略

- **周期**：`tasks` 每 2 分钟一次轻同步（账号 + 隧道），不拉节点列表（节点变动慢，省两次外部请求）；
  轻同步每平台仅 2 个上游请求，2 分钟对上游是零感知频率（性能审查 2026-09：3min→2min）。
- **手动同步**：`?full=1` 连节点一起拉；每平台一把锁，与周期任务串行。
- **失败不覆盖**：任一环节失败只写 `last_error` + 降级状态，**保留上次成功的镜像**，
  平台临时抖动时面板仍能展示有效数据。
- **写操作后立即轻同步**：新建/删除隧道后马上回读，避免用户手动刷新。

## 8. 前端（/admin/frp，懒加载 chunk ~11.7KB gzip）

页面结构（v2.1 归一化改版）：

1. **平台卡**（纯展示，不切换下方内容）：平台名 + 状态标签 + 四格特色指标
   （隧道在线/配额、剩余流量或累计上传、签到或累计下载）+ 行内操作（同步/换密钥或重新授权/解绑）；
   用户名等账号画像不出现在卡片标题。
2. **账号用量**：跨平台归一化的键值瓦片，每平台一块（今日流量 / 剩余流量或累计上传下载 / 限速 / 上次同步）。
3. **流量历史**：一张图两条曲线（NATFRP 蓝、ChmlFrp 紫），day 口径同为 7 点天然对齐。
4. **隧道**：跨平台合并表，`平台` 列标注归属；操作列按平台能力渲染
   （NATFRP：编辑/配置/锁定/迁移/认证/删除；ChmlFrp：编辑/配置/下线/删除）。
   「新建隧道」弹窗顶部选平台，节点候选跟随所选平台的镜像。
5. **在用节点**：合并表（`平台` 列标注归属），只列被隧道挂载的节点；
   「未在用节点（N）」默认折叠（虚线描边手风琴），建隧道/迁移在弹窗下拉中选节点，不依赖这张全量表。
6. **免费二级域名**：ChmlFrp 特有区块独立成卡（后端接口按平台挂载）。

弹窗：绑定 NATFRP、设备码授权、建/改隧道（含平台选择）、迁移、锁定、解析、危险确认。

- 视图只读 store、只调 actions，不直连 API 门面（doc/10）；
- store 的 `frpDetails` 按平台 id 存详情（双平台同屏，不再是单选模型），
  写操作后只刷新对应平台那份；
- 设备码授权弹窗按 3 秒轮询后端（后端已按平台 `interval` 节流，前端多问不会多打上游）；
- 配置下载走裸 `fetch` + blob（doc/10 §8 明示的唯一下载例外），`revokeObjectURL` 已调用；
- 状态一律「颜色 + 文字」双通道；破坏性操作走 `ConfirmDialog`。

## 9. 安全

- 凭据 AES-256-GCM 加密落库（复用 `internal/crypto`，与 SSH 凭据同一主密钥）；
- 接口层只下发 `has_token`，`store.FRPPlatform.TokenEnc/RefreshEnc` 标 `json:"-"`；
- **ChmlFrp 的 `/nodeinfo` 会返回节点级 `apitoken`/`nodetoken`**，本模块**不调用该端点**；
  联调脚本里对该字段做了打码，避免进入日志；
- 平台返回的 `auth.token`（frpc 配置内）只在用户主动点「配置」时以附件下发，不落库；
- 下载文件名经 `sanitizeFileName` 白名单过滤（隧道名可能含任意字符）；
- 所有写操作进审计日志（`frp_platform_bind`、`frp_tunnel_create` 等）。

## 12. 游客面板暴露面（/tunnels，v2.1 新增）

管理端看全量，游客端只看「用得多不多、通不通」。公开页多一个入口就必须多问一次
「这条数据是平台的公开信息，还是我的账号信息」——本模块的答案是后者一律不下发。

### 12.1 接口与字段白名单

`GET /api/v1/public/frp`（无鉴权；`private_mode=true` 且未登录时 401/1002），
响应体就是白名单，详见 [doc/04 §1.5](./04-API接口设计.md)：

| 下发 | 不下发 |
| --- | --- |
| 平台展示名、`kind`、同步是否正常 | 用户名 / UID / 实名 / 账号分组 |
| 隧道总数 / 在线数 / 连接数 | 剩余流量、限速（套餐与资费信息） |
| 今日流量消耗（两平台各自口径归一） | 节点域名 `host`、节点 `remote_id` |
| **在用**节点的名称、分组、在线、负载、在线时长 | 隧道名、本地/内网端点、公网端点 |
| 上次同步时间 | 平台的错误原文（`last_error`） |

### 12.2 节点只给「在用的」

平台节点表是全网节点（NATFRP 实测 71 条、ChmlFrp 39 条），对访客既无信息量又等于公开
未使用的拓扑。`store.ListFRPNodesInUse` 按「隧道记录里的 `node_id` = 节点 `remote_id`」关联，
只回被本账号隧道挂载的节点；管理端保留全网列表但标记 `in_use`，并在 UI 上
「在用展开 / 未在用折叠」。注意 ChmlFrp 的 `/tunnel` 只返回节点名不返回节点 ID，
`runner.fillNodeNames` 会按名称反查节点镜像补齐 `node_id`（首次同步若节点镜像尚未
落库，下一轮 full 同步补上）——漏了这一步 ChmlFrp 的 in_use 永远匹配不到。

### 12.3 前端

`views/monitor/TunnelView.vue`（路由 `/tunnels`，懒加载 2.6KB gzip，不进公开首屏）：
KPI 条（今日流量 / 在线隧道 / 在用节点 / 连接数）+ 每平台一张玻璃卡（用量三栏 + 在用节点列表 + 负载条）。
数据源是 `stores/monitor.js` 的 `startFrp/stopFrp`——**独立 60 秒低频轮询**，
挂载时启动、离开页面即清定时器（后台每 2 分钟才同步一次平台，跟着 10 秒主轮询纯属浪费）。

### 12.4 回归测试

`internal/handler/frp_public_test.go` 不只断言「该给的」出现，更对响应体做
**禁止串扫描**（账号名 / UID / 实名 / 限速 / 剩余流量字段 / 节点域名 / 隧道名 / 端点 / 内网地址 /
`token` / `remote_id`），任一命中即测试失败——白名单是纪律，不是自觉。


## 13. 客户端容器化（v2.2 新增：deploy/frpc-*）

面板管的是**本机**的穿透：隧道建好后，还需要一台跑 frpc 的机器把流量送到
`local_ip:local_port`。为了让干净服务器上「装完面板就能用」，两个平台的客户端打成
本仓库镜像，与面板同一个 GHCR 命名空间，`docker compose up -d` 即用。

| 镜像 | 基底 | 版本 pin | 说明 |
| --- | --- | --- | --- |
| `ghcr.io/yoahoug/beacontower-frpc-natfrp` | 官方 `natfrp/frpc`（scratch，静态二进制）二次封装进 alpine | `0.51.0-sakura-14` | 保留官方环境变量模式（`NATFRP_TOKEN`/`NATFRP_TARGET`），另支持挂载配置文件 |
| `ghcr.io/yoahoug/beacontower-frpc-chmlfrp` | alpine + 上游 `fatedier/frp` release 二进制 | `0.61.2` | ChmlFrp 只是服务端，客户端用上游 frp 即可（与 ops 长期在跑的二进制 sha256 一致） |

关键结论与坑：

- **NATFRP 的配置格式由 `frpc` 参数决定**：声明樱花分支版本返回 INI（`sakura_mode = true`），
  声明上游版本（如 0.59.0）返回 TOML。镜像 pin 的是樱花分支，所以面板固定声明
  `NatfrpFrpcVersion = 0.51.0-sakura-14`（`internal/frp/natfrp.go`）——**升级镜像版本要同步改这个常量**。
- **ChmlFrp 客户端不必用它的魔改分支**：其官方仓库 `TechCat-Team/ChmlFrp-Frp` 是
  frp 0.51.2 的旧魔改（quic-go 卡在 Go 1.20），而上游 frp 0.61.2 直接可登录、可起隧道，
  与 ops 现役容器的二进制 sha256 完全一致（`8b82594c…`），所以取上游 release 更省事也更安全。
- **必须是 host 网络**：隧道配置里的 `local_ip` 通常是 `localhost`/`127.0.0.1`，
  指本机服务；bridge 网络下容器里的 localhost 是容器自己，隧道会 502。
  compose 默认 `network_mode: host`，要用 bridge 得把 `local_ip` 改成宿主机地址。
- 构建**不跟随 main 推送**：`.github/workflows/frpc-images.yml` 只有 `workflow_dispatch`
  （可用输入覆盖版本号），避免主线迭代时反复重建第三方客户端镜像。

### 13.1 ChmlFrp 接口实测踩坑（2026-09-30 全新云主机）

ChmlFrp 的文档滞后于实现，以下约束全部来自真机反复试错（面板已按此加固，均有单测）：

| 坑 | 现象 | 面板处置 |
| --- | --- | --- |
| `node` 参数要**节点名**不是数字 id | 传 `remote_id` 建隧道报「节点不存在」；节点列表里数字 id 还跨分组重复（VIP 组/普通组） | `runner.chmlNodeName` 按 `(platform_id, remote_id)` 反查名字再发（`pickChmlNodeName` 单测覆盖同名跨平台情形） |
| `/update_tunnel` 必须带 `porttype` | 其它字段都对也报「端口类型缺失」 | 改隧道时补发 `porttype`（取原隧道协议，未传则用库里现值） |
| 隧道名仅 `^[A-Za-z0-9_]+$` | 带连字符/中文/空格 →「隧道名不符合规范」 | 表单前置校验并给出明确文案，不把平台原文错误直接甩给用户 |
| `remote_port` 必须在节点允许范围内 | 留 0 想让平台自动选 →「指定的端口不在允许的范围内」；被占用 →「该远程端口已被占用」 | 占位提示写明「0 平台不会代选、允许范围以节点页为准」，平台错误原样透出供用户改端口 |

另：免费账号实测可稳定开 2 条隧道（HTTP + SSH），删除后端口立即可复用；同一账号
在 ops 与测评机上并存时，新隧道不要占已被现役隧道使用的远端端口。

### 13.2 隧道「真的通了」的验证方法（可复用）

隧道状态显示 normal / 客户端日志 `start proxy success` 都只证明**控制面**成功，不能证明
数据面穿通。可复用的铁证方法（2026-09-30 实测，ChmlFrp 英国伦敦节点）：

1. 在被穿透的机器上起一个**只监听环回**的标记服务（`127.0.0.1:18099`，公网与安全组
   都到不了），页面里放一次性随机 token；
2. 用面板建隧道指向它（`local_ip=127.0.0.1`、`local_port=18099`），下载面板给的配置，
   用 `deploy/frpc-chmlfrp` 镜像跑客户端（`--network host` + 配置只读挂载）；
3. 从**公网另一台机器**访问隧道的公开地址（如 `http://<节点IP>:34282/`），能取到那个
   token 才算通。
4. **必须带对照组**：直连被穿透机器的 18099 应失败（证明 token 只可能来自隧道），
   访问错误的远端端口应失败（证明不是中间设备乱答）。实测三项结果分别为
   200+token / 连接失败 / 连接失败。

HTTP 之外再补一条 SSH 型隧道（`local_port=22`），用 `nc <节点IP> <remote_port>` 读
banner，返回被穿透机器的 `SSH-2.0-OpenSSH_*` 即证明任意 TCP 协议可穿。

产物清理：删除面板里的隧道记录（会同步删平台侧）+ 停掉客户端容器 + 关掉标记服务。

### 13.3 NATFRP（樱花）实测补充（2026-09-30，含官方 launcher 托管恢复）

**节点会拦截 TCP 隧道上的明文 HTTP**。用 `curl http://<节点>:<remote_port>/` 探测会收到
节点自己渲染的 501 合规页（「执行机房的内容合规要求和有关部门的管控规定 / 请启用 HTTPS」），
数据并没有到达你的服务——容易误判成「隧道没通」。同一服务改用 TLS 承载（自签名即可）
再访问即 200 正常返回。**验证 NATFRP TCP 隧道要么用 HTTPS，要么用非 HTTP 协议（如读 SSH
banner），不要用明文 HTTP**。

**隧道删除后按原参数重建，远端端口保持不变**：实测把「ssh / 长沙电信PLUS2 / localhost:22 /
remote 29377」删掉后以相同参数重建（面板隧道的 `remote_port` 传 29377），平台仍分配 29377，
公网地址 `<节点域名>:29377` 不变，使用端无需改配置。面板的 NATFRP 建隧道支持指定
`remote`（tcp/udp 传端口号，0 = 平台分配；http/https 传绑定域名）。

**官方 `natfrp/launcher` 托管隧道的恢复步骤**（ops 现网即此形态：`natfrp/launcher` 容器、
host 网络、配置目录挂载到 `/run`）：launcher 用配置 JSON 里的 `auto_start_tunnels`
（隧道 ID 列表）决定启动哪些隧道，隧道被删后日志报「隧道不存在」/「api error: 404」并
放弃该隧道。恢复：①面板按原参数重建隧道拿到新 ID；②停 launcher 容器；③备份配置 JSON，
把列表里的旧 ID 换成新 ID；④起容器，日志出现「隧道启动成功」即可。
注意 launcher 与 frpc 客户端**不能同时在线**（平台报「当前隧道已在线，请勿重复开启」），
交接时先把临时客户端停掉。

**验证「隧道后面到底是哪台机器」用 host key 指纹**：`ssh-keyscan -p <port> <节点域名>`
取指纹与目标机 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` 比对。banner 不可靠
（同为 Ubuntu 24.04 的两台机器 banner 只差补丁号，容易看走眼）。

## 14. 客户端托管（v2.3 新增：面板经 SSH 把 frpc 装到任意节点）

### 14.1 为什么要有这一层

v2.2 把客户端容器化了，但落地方式是「面板下载 ini → 你 SSH 上服务器 → 改 compose → 起容器」。
这与本项目的立意冲突：**面板本身就有节点 SSH 通道（采集/WG 组网都用它），凭什么穿透还要用户自己登录机器**。
§13 的两个镜像是给「面板托管」用的，手工 compose 只是没有 SSH 凭据时的退路。

于是 v2.3 起，隧道页多一个「托管」入口：选平台 + 选节点 + 勾隧道，剩下的全由面板做——

1. `docker --version` / `docker info` 探测节点；缺 Docker 且用户勾了「自动安装」时按包管理器自动装
   （apt 会先 `apt-get update`，dnf/yum、apk、pacman 各一条命令，装完轮询 `docker info` 最多 20s 等守护进程起来）；
2. 按勾选的隧道逐条向平台取「[common] + 单隧道段」配置，合成一份完整 ini；
3. 经 SSH stdin 落盘到 `/etc/beacontower-frpc/<kind>/frpc.ini`（`chmod 600` + 目录 `700`，落盘走临时文件再 `mv`，不落到 argv/日志）；
4. `docker image inspect || docker pull` 拉镜像（GHCR；国内节点可达，Docker Hub 不行）；
5. `docker rm -f` 旧容器 + `docker run -d --restart unless-stopped --network host` 起新容器（挂载配置只读）；
6. 2 秒后回读 `docker inspect` 状态与 `docker logs --tail 30`，失败时把日志尾三行塞进错误信息（用户一眼能看到 `proxy conflict`、`login to server failed` 之类）。

同一节点同一平台只托管一份客户端（唯一索引 `frp_deploy(platform_id, server_id)`）：
一份 ini 可以同时跑多条隧道，多条隧道共用一份 `[common]`（登录凭据），分开跑反而会重复登录。

### 14.2 安全边界（谁能碰容器）

面板只碰**自己造的**容器：`beacontower-frpc-<kind>-<server_id>`，名字由面板生成（正则白名单
`^[a-z0-9][a-z0-9_.-]{0,62}$`），并带 `beacontower.managed=frpc` 标签。所有动作（restart/stop/start）先跑

```sh
docker inspect -f '{{index .Config.Labels "beacontower.managed"}}' <容器> | grep -q '^frpc$'
```

验过标签才动作，因此用户手搓的同名容器、别人的容器都不会被误伤。移除托管时 `docker rm -f` + 删
`/etc/beacontower-frpc/<kind>/`；解绑平台会连带清理该平台在**所有**节点上的托管容器与配置（失败只记日志不阻塞解绑）。

配置里含平台 token：只经 SSH stdin 写盘（不进命令行、不进面板日志），下载接口一次性返回给浏览器，
节点侧权限 600；错误信息里的日志尾三行可能含隧道名，但不会有凭据。

### 14.3 「隧道改了要重新同步」怎么知道

平台侧隧道一旦增删改，节点上那份 ini 就过期了。面板不猜，直接打脏标：
`FRPTunnelUpdate` / `FRPTunnelDelete` 成功后调 `MarkFRPDeploysDirtyByTunnel`，把引用了这条隧道的
托管记录置 `dirty=1`，前端显示「待同步」徽标，用户点「同步配置」后清 0（同步失败保留脏标，
提示里带失败原因）。托管列表也可以点「刷新状态」实时回读节点容器（`?refresh=1`，逐台 SSH）。

容器状态在面板侧被归一成四种（"running" 之后写库的就是这四个值，前端标签一一对应）：
`running`（含 restarting）/ `stopped`（exited、created、paused）/ `missing`（容器被删）/ `error`（dead）。

### 14.4 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/admin/frp/deployments` | 托管列表，`?refresh=1` 时逐台 SSH 回读真实状态 |
| POST | `/api/v1/admin/frp/deployments` | 部署/更新托管（唯一键 = 平台+节点，重复提交等价于重新同步） |
| POST | `/api/v1/admin/frp/deployments/:id/sync` | 重新拉配置 + 重建容器 |
| POST | `/api/v1/admin/frp/deployments/:id/action` | `restart` / `stop` / `start` |
| POST | `/api/v1/admin/frp/deployments/:id/status` | 回读单条状态 |
| GET | `/api/v1/admin/frp/deployments/:id/logs?tail=200` | 容器日志尾部（1–500 行） |
| DELETE | `/api/v1/admin/frp/deployments/:id` | 移除托管（`?keep=1` 只删记录、保留节点上的容器） |
| POST | `/api/v1/admin/frp/servers/:id/docker` | `{install:false}` 探测 / `{install:true}` 自动安装（可能好几分钟） |

错误码沿用 §6：`2023` = 节点侧操作失败（SSH/Docker/容器），`2024` = 节点需要 Docker（前端据此提示勾「自动安装」）。
耗时差异大：探测/动作/日志 45s，部署与同步 6 分钟，装 Docker 12 分钟（面板 HTTP 无写超时，前端按调用分别给 60s/6min/12min）。

### 14.5 真机 E2E（2026-09-30，阿里云全新 Ubuntu 24.04 + 本地面板）

| 项 | 证据 |
| --- | --- |
| 一键装 Docker | 节点装前无 docker；`/var/log/apt/history.log` 出现 `apt-get install -y -qq docker.io`（面板生成），随后 `docker --version` = 29.1.3 |
| 拉镜像 | 节点 `docker images` 出现 `ghcr.io/yoahoug/beacontower-frpc-natfrp:latest`（23.2MB，GHCR 国内可达） |
| 配置落盘 | `/etc/beacontower-frpc/natfrp/frpc.ini` 权限 `600 root:root`、目录 `700`；内容为 `[common]`+`[New]` 段（凭据脱敏后核对） |
| 容器形态 | `docker inspect`：`--network host`、`--restart unless-stopped`、`beacontower.managed=frpc` 标签、配置只读挂载 |
| 状态/日志 | `?refresh=1` 回读 running；`/logs` 返回 frpc 启动日志与 `start error: proxy conflict` |
| 脏标 | 改隧道 → `dirty=1`；同步 → 清 0（同步失败保留） |
| 解绑清理 | 解绑平台 → 面板托管记录 0 条、节点容器 0 个、`/etc/beacontower-frpc` 空 |
| 前端 | 隧道行「托管」按钮、客户端托管卡片、部署弹窗（节点下拉按 `ssh_ready` 置灰、已托管节点标注）、日志弹窗，全部与页面既有控件同款 |

**一个刻意的负面对照**：本次 E2E 用的是账号里的隧道 `New`——ops 上的 launcher 正在服务它，
节点上的 frpc 因此稳定报 `proxy conflict`（平台侧一条隧道同时只允许一个客户端在线）。
这恰好证明「谁在线谁服务」由平台裁决，**面板托管不会顶掉正在跑的客户端**（对照 §13.3 的
launcher 交接注意事项）；也正因为如此，数据面（公网地址真的回到这台新节点）必须用一条
**独占隧道**才能验，见 §14.6。

### 14.6 数据面复验（待独占隧道）

复验方法沿用 §13.2 的四件套（回环监听 + 一次性 token + 正反对照 + 公网口取回），
把 §13.2 的客户端容器换成「面板托管部署的容器」即可，其它不变。
