# 02 · 总体架构与技术选型

## 1. 架构总览

```
                        ┌────────────────────────────────────────────┐
                        │            BeaconTower 容器 (Docker)        │
                        │                                            │
浏览器 / 访客 ──HTTPS──▶ │  ┌──────────┐   ┌──────────────────────┐   │
  公开状态页(只读)       │  │ Gin HTTP │   │  前端静态资源 (embed) │   │
  /admin  管理后台       │  │  Server  │──▶│  Vue3 + Vite 构建    │   │
                        │  └────┬─────┘   └──────────────────────┘   │
                        │       │                                    │
                        │  ┌────▼─────────────┐   ┌──────────────┐  │
                        │  │ Collector 采集器  │──▶│ SQLite (WAL) │  │
                        │  │ 每节点协程+tick  │   │ /app/data    │  │
                        │  └────┬─────────────┘   └──────────────┘  │
                        └───────┼────────────────────────────────────┘
                                │ SSH (golang.org/x/crypto/ssh)
                                │ 仅出站连接，被监控机零安装
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
        被监控机 A         被监控机 B         被监控机 C
        (Ubuntu/KVM)      (Debian/物理机)    (AlmaLinux/容器)
        执行只读命令：      读取 /proc、df、    输出 key=value
        uname/os-release   /proc/net/dev 等   文本，面板侧解析
```

要点：

1. **单进程**：HTTP 服务、采集器、SQLite 全在一个 Go 进程内；
2. **仅出站**：面板主动 SSH 到被监控机，被监控机无需开放任何额外端口，也无需安装/运行任何东西；
3. **推拉结合**：指标为面板定时拉取；前端页面通过 SSE 从面板拉实时快照，前端永不接触被监控机。

## 2. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端语言 | **Go 1.26+** | 单二进制、交叉编译易、并发模型契合"多节点并行轮询"场景、内存占用低 |
| HTTP 框架 | **Gin** | 生态成熟、中间件丰富（限速/恢复/日志）、Nezha 同款，资料多 |
| SSH 库 | **golang.org/x/crypto/ssh** | 官方维护，支持密码/密钥认证、host key 校验 |
| 数据库 | **SQLite**（modernc.org/sqlite 纯 Go 驱动） | 见下节论证；纯 Go 驱动无 CGO，Docker 构建与交叉编译零负担 |
| 实时推送 | **SSE**（Server-Sent Events） | 单向推送足够；文本协议、断线重连内建、无 WebSocket 的代理兼容问题 |
| 前端框架 | **Vue 3 + Vite + Vue Router** | 原型已落地；后续按需引入 Pinia 与 ECharts（仅详情页图表） |
| 状态管理 | 先组件内 + composable，规模变大再引 Pinia | 卡片面板状态简单，避免过度设计 |
| 部署 | **Docker 多阶段构建 → 单镜像** | 见 07 文档 |

## 3. 为什么不需要"专门的数据库"

结论：**用内嵌 SQLite（单文件），不引入任何独立数据库服务。**

- **写入压力极小**：100 台 × 每 10s 一条采样 ≈ 10 写/秒，SQLite + WAL 轻松支撑（实测可达数万写/秒）；
- **读写比悬殊**：面板绝大多数请求是读快照与聚合曲线，SQLite 读性能绰绰有余；
- **零运维**：没有第二个容器、没有连接池调优、没有用户密码管理；
- **备份 = 复制文件**：`data/` 目录整个 rsync 即可，符合个人自托管的心智模型；
- **迁移余地**：全部经 `database/sql` 访问，若未来规模上千节点需换 PostgreSQL，仅替换驱动与个别方言 SQL。

辅助手段：原始采样只保留短窗口，长历史用聚合表（见 03 文档），进一步压低写入量。

## 4. SSH 无 Agent 采集设计（本项目核心）

### 4.1 与 Nezha 的根本差异

Nezha 采用 "Agent 常驻 + gRPC 上报"：功能强（计划任务、DDNS 等），但需要每台机器安装进程。
本项目采用 **Agentless（无 Agent）**：

| 维度 | Nezha (Agent) | BeaconTower (SSH) |
| --- | --- | --- |
| 被监控机侵入性 | 需安装常驻 Agent | 零安装，仅用 SSH |
| 采集实时性 | 秒级推送，可更低间隔 | 轮询式，建议 ≥5s |
| 可执行功能 | 命令下发、计划任务等 | 只读采集（刻意为之，缩小攻击面） |
| 认证 | Agent 密钥 | SSH 原生认证（密码/密钥） |
| 规模上限 | 数千台 | 约 100 台（SSH 连接开销决定） |

借鉴自 Nezha 的部分见 `doc/08` 附录；此差异是用户明确需求（SSH 连接），且"只读"使被监控机风险面最小化。

### 4.2 采集协议：单次 exec，文本 key=value

每轮采集对每台机器**只执行一次**远端 `sh` 命令（`sh -s`，脚本经 SSH 会话 stdin 传入，避免多次往返与一切引号拼装），将 `/proc`、`df` 等只读信息拼成多行 `key=value` 文本输出，面板侧统一解析：

```sh
sh -c '
echo "up_s=$(cut -d. -f1 /proc/uptime)"
echo "load1=$(cut -d" " -f1 /proc/loadavg)"; ...
cat /proc/stat | grep "^cpu ";  cat /proc/meminfo | egrep "^(MemTotal|MemAvailable|SwapTotal|SwapFree)"
grep "^cpu " /proc/stat;  awk "/^cpu /{print \$2,\$3,\$4,\$5,\$6}" /proc/stat  (前后两次采样差算使用率，见 4.3)
cat /proc/net/dev;  ss -s 或 /proc/net/tcp{,6} 计数; df -kP; uname -m; cat /etc/os-release ...
'
```

- 网速：两次采集间 `/proc/net/dev` 字节计数差 ÷ 实际间隔，得到 bps；
- CPU：两次采集间 `/proc/stat` jiffies 差值计算使用率（面板侧保存上次读数）；
- 连接数：解析 `/proc/net/tcp{,6}` 行数（无需 ss/lsof 依赖）；
- 全部命令为 POSIX sh + 只读文件，目标机无需 jq/lsof 等额外工具；执行超时 8s，超时记失败。

### 4.3 调度与容错

- 每节点一个 goroutine + `time.Ticker`，**随机抖动（jitter）**避免所有节点同时建连；
- SSH 连接每轮新建（短连接，简单可靠），后续如需降开销可改为连接复用；
- 失败处理：指数退避重试；连续 3 次失败标记 `offline`（前端红卡），恢复自动转回；
- Host Key 校验：首次连接记录指纹（TOFU，信任并记录），管理后台展示指纹供人工核对；可开启严格模式（指纹不匹配即拒绝）；
- 系统画像（os-release / CPU 型号 / 磁盘列表等变更频率低的数据）首次连接回读，之后每日刷新。

## 5. 目录结构与前后端分离（对齐 new-api 的单容器方案）

> 明确约束：**最终只跑一个容器、一个进程、一个端口**。前后端仅在"开发期"是两个独立进程（前端 dev server + 后端），构建产物合入同一个二进制。分离逻辑参考 new-api（QuantumNous/new-api）的实现。

```
BeaconTower/
├── doc/                      # 本开发方案
├── web/                      # 前端工程（Vue3，独立 package.json，可独立开发/构建）
│   ├── src/{components,views,composables,mock,utils,styles,router}
│   └── dist/                 # 构建产物（构建期生成，被 go:embed）
├── main.go                   # Go 入口：//go:embed web/dist
├── internal/
│   ├── router/               # 路由装配 + web-router（SPA 回退，含 WebAssets 抽象）
│   ├── handler/              # admin / public API handlers
│   ├── middleware/           # 会话、CSRF、限速、安全头、gzip
│   ├── collector/            # SSH 采集器（核心，含公网 IP 定位探测）
│   ├── geoip/                # IP 归属地解析：离线 mmdb 优先，在线回显服务回退，结果缓存
│   ├── store/                # SQLite 访问层
│   ├── crypto/               # AES-GCM、Argon2id
│   └── config/
├── go.mod                    # Go module 位于仓库根（与 new-api 一致）
├── Dockerfile                # 多阶段：node build → go build → 运行镜像
├── docker-compose.yml
└── README.md
```

### 分离机制四阶段（new-api 同款）

| 阶段 | 形态 | 说明 |
| --- | --- | --- |
| 开发期 | 两个进程 | `web/` 下 Vite dev server 独立运行，`/api` 通过 dev proxy 转发到本地 Go 后端端口；Go 侧用 `//go:build dev` 变体直接读磁盘上的 `web/dist`（或不挂前端），互不阻塞 |
| 构建期 | 两次构建 | `npm run build` 产出 `web/dist` → Go 构建时 `//go:embed web/dist` 打进二进制（new-api 的 `buildFS` + `indexPage` 两变量模式） |
| 运行期 | 一个进程 | 单端口同时服务 API 与静态资源；`WebAssets{BuildFS, IndexPage}` 抽象把"资源从哪来"与路由逻辑解耦 |
| 部署期 | 一个容器 | 多阶段 Dockerfile，最终镜像 = 二进制 + data 卷，见 07 文档 |

### SPA 回退规则（web-router 的 NoRoute 兜底，new-api 同款）

1. 请求命中静态资源 → 直接返回（gzip + 带 hash 的长缓存）；
2. 未命中且路径以 `/api` 开头 → 返回 **JSON 404**（绝不把 index.html 当 API 响应，避免前端拿到 HTML 报解析错）；
3. 其余未命中路径（如 `/admin/servers` 刷新）→ 返回 `index.html`（`Cache-Control: no-cache`），交给前端 history 路由。

预留 `FRONTEND_BASE_URL` 环境变量（new-api 同款开关）：设置后页面类请求 302 到独立前端地址，默认不启用——保留"前端可独立部署"的退路，但默认单容器交付。

## 6. 请求链路（运行时）

1. 前端加载后订阅 `GET /api/v1/public/stream`（SSE），先收到全量快照，之后每轮采集后收到增量更新；
2. 历史曲线走 `GET /api/v1/public/servers/:id/history`（聚合表查询）；
3. 管理操作全部走 `/api/v1/admin/*`，Cookie 会话 + CSRF，见 04/05 文档；
4. 采集器每轮把快照写入内存 + 落库（采样表），并触发 SSE 广播；
5. **地区自动定位**：试连/每日画像刷新时经 SSH 回读节点公网出口 IP，`geoip` 模块解析出国家/地区（城市可选）写回 `server.region`（仅 `region_source=auto` 的节点），公开链路只见文案不见 IP（见 04/05 文档）。
