# 18 · 双前端主题架构（v2.8）

> v2.8 起 BeaconTower 前端解耦为两套独立应用、按「主题」组织：根路径 `/` 是默认主题
> **toy**（Neubrutalism），经典玻璃拟态迁至 `/classic/`。本文固化主题拓扑、localStorage
> 契约与新增主题的标准步骤，后续主题（复古终端、赛博霓虹等）按约定即插即用。

## 1. 拓扑与路由（internal/router/router.go）

```
GET /                       → 默认主题（toy）index.html + 静态资源
GET /?theme=<id>            → 302 到 <挂载路径>?theme=<id>（如 /classic/?theme=classic），
                              未知 ID / 默认主题落回默认 index；参数留给目标端 boot 脚本
                              写偏好（显式覆盖），不带参会被旧偏好弹回原主题
GET /classic/...            → classic 主题（资源/根文件/SPA 回退都在此前缀下）
GET /api/...                → 与主题无关，同一组 API 服务所有主题
```

- 主题注册表：`registerThemes()` 按「默认优先」的顺序返回 `themeApp{id, mountPath, fs, index}`；
  `main.go` 两个 `//go:embed all:web/dist`（classic）与 `all:web-toy/dist`（toy）编译期打进二进制。
- 静态作用域按前缀隔离：`/assets`、`/icons`、`workbox-*.js`、`sw.js`、`manifest.webmanifest`、
  `boot-theme.js`、`favicon.ico`、`robots.txt` 各主题一份，互不串扰；带 hash 资源长缓存（immutable），
  根级文件短缓存语义（`boot-theme.js` 例外：no-cache，拓扑必须与部署一致），SPA 回退分别落到各自 `index.html`。
- **classic 的 Vite `base: '/classic/'` 是硬约束**：产物里 assets/manifest/icons/SW/registerSW 的 URL
  全按此生成，缺了它浏览器会去根作用域取 classic 资源（被 toy 作用域接管）→ 404 → 切到 classic 白屏。
- 存在性优雅降级：某主题缺 favicon → 404（不吐 HTML）；缺 manifest/robots → 回退该主题
  index.html（不把 `text/html` 给会校验 MIME 的请求方）；缺 boot-theme.js → 404（脚本语义，
  回吐 HTML 只会被 nosniff 拒绝、静默不执行）。toy 无 PWA/manifest 是预期行为。

### 根 `/sw.js` = 退役 Service Worker

v2.7 及之前 classic 的 Workbox 预缓存 SW 注册在**根 scope**。已安装 PWA 的老用户（iPhone）
若不处理，导航 `/` 会永远命中旧缓存的 classic 壳——又一类「强刷无效」。处置：

- 根 `/sw.js`（Cache-Control: no-cache）返回 `web-toy/public/sw-retire.js`：
  `skipWaiting` → 清空全部 Cache Storage → 逐个 `client.navigate()` 刷新受控页 →
  `registration.unregister()`。浏览器 SW 更新检查取到即完成迁出，老 PWA 用户下次打开落到 toy。
- classic 自己的 SW 在 `/classic/sw.js`（Workbox 预缓存照常工作，scope 天然被前缀隔离）。

## 2. 前端双应用与切换闭环

| | web-toy（默认） | web（classic） |
| --- | --- | --- |
| 路径 | `/` | `/classic/` |
| 栈 | Vue3 + TS + Tailwind（Vite 6） | Vue3 + Pinia + ECharts + PWA |
| dev 端口 | 5174（`npm run dev:toy`，/api 代理 8080） | 5173（`npm run dev:classic`） |
| 数据层 | `src/services/{http,real,api}.ts` | `src/api/{http,monitor,admin,auth}.js` |
| 主题清单 | `src/theme.ts` | `src/theme.js` |

**localStorage 契约**（两套前端 + 未来主题共同遵守）：

| key | 值 | 语义 |
| --- | --- | --- |
| `beacontower_preferred_theme` | `toy` \| `classic` | 主题偏好，双向切换时由目标端写入 |
| `beacontower_avatar_mode` | `bot` \| `os` | toy 头像偏好（保持兼容，classic 不读） |

**切换机制（无重定向死循环）**：

1. 双方 `index.html` 顶部各引一个**同源外部同步脚本** `boot-theme.js`（各前端 `public/` 产物，
   模块加载前执行，防闪屏；后端按主题作用域提供，no-cache）：
   - 带 `?theme=<id>` → 写偏好并 `location.replace()` 到该主题路径（顺带清参）；
   - 无参且「偏好 ≠ 当前主题」→ `replace()` 过去；相等则原地渲染；
   - dev 端口（5173/5174）直接跳过：两端口各服务一套前端，跨主题由切换入口按端口直跳。
   - **不能内联**：应用 CSP 是 `default-src 'self'`（无 script-src/nonce），内联脚本会被
     浏览器拦掉且只在控制台留一条 violation——属于「静默失效」，v2.8 首发踩过。
2. 切换入口：toy 侧栏左下「主题」坞 → `ThemeSwitcherModal`；classic 侧栏底部「🎨 主题」
   → `ThemeCenter`（信息结构同构）。跳转前写偏好，生产环境直接 `location.href` 到挂载路径
   （dev 跨端口联调保留 5173↔5174 分支）。
3. 两端各持一份**同构 THEME 清单**（id/name/desc/path/icon/available），清单渲染切换卡片，
   未上线主题显示「即将推出」。

## 3. toy 数据层（v2.8 真实联调）

- `services/http.ts`：唯一网络出口。同源 fetch + 会话 cookie；非 GET 自动附
  `X-CSRF-Token`（读 `bt_csrf` cookie）；`{code,msg,data}` 解包，1002/1005/1006 归一化
  `ApiError`；非幂等请求不重试——语义与 classic `web/src/api/http.js` 完全一致。
- `services/real.ts`：端点逐一映射 `internal/router/router.go`（公开 7 个含 SSE；
  管理端 servers/settings/audit/wg/frp 全量）。SSE `EventSource` 订阅 `snapshot`/`update`/
  `ping` 三种事件，断线 3s→30s 指数退避；顶部「实时同步」开关即 SSE 的 pause/resume。
- `services/api.ts`：门面。**生产默认 real**；`mock.ts` 仅在显式 `VITE_API_MODE=mock` 的
  dev 会话动态加载（且 format 工具已拆到 `services/format.ts`，生产 bundle 不含仿真引擎）。
- 契约红线：后端没有的能力不假装成功——FRP 隧道「重启」（平台 API 未开放）与 ChmlFrp
  静态 token 绑定（走设备码授权）都会如实报错；会话列表后端无端点，安全页只保留改密
  （后端语义：改密热更新并吊销其余会话）。
- 登录走真实 `/admin/login`（用户名+密码），无任何 mock token 后门。

## 4. 新增主题标准步骤（三步）

1. **新前端目录**：如 `web-terminal/`（Vue3 + 独立 Vite，`base: '/terminal/'`），实现 THEME
   清单同构文件并放一份 `public/boot-theme.js`（THEMES 表中自己的 `current: true`）；
   根 `package.json` 加 `build:terminal` / `dev:terminal`。
2. **进镜像**：`Dockerfile` 加 `frontend-terminal` 阶段 + backend `COPY --from` 到
   `./web-terminal/dist`；`main.go` 加 `//go:embed all:web-terminal/dist`；
   `router.go registerThemes()` 注册 `{id: "terminal", mountPath: "/terminal/"}`；
   `.dockerignore` 加 `web-terminal/node_modules/ web-terminal/dist/`；
   `.gitignore` 加 `web-terminal/dist/*` + `!web-terminal/dist/.placeholder`。
3. **清单各加一行**：`web-toy/src/theme.ts` 与 `web/src/theme.js`（id/path 必须与注册表
   一致），切换卡片自动出现；同时更新**各主题 boot-theme.js 里的 THEMES 表**（path/current
   必须与注册表一致，否则偏好迁移会跳错或刷屏）。若要换默认主题，调整 `registerThemes()`
   顺序（第一个为默认）。

## 5. 构建与发布

- 本地一键构建：`./scripts/build.sh`（两套前端 → `go build`；`go:embed` 编译期要求两个
  dist 存在，仓库内 `.placeholder` 兜底，真实构建产物会覆盖）。
- CI：push main 自动构建镜像（Dockerfile 三阶段并行：frontend-toy / frontend-classic /
  backend），服务器 `docker compose pull && up -d` 滚动更新（doc/11 SOP）。
- 发布后验证清单：`/` = toy、`/classic/` = classic、`/?theme=classic` 302 到
  `/classic/?theme=classic`、classic 产物引用全部带 `/classic/` 前缀（`/classic/assets/*`
  长缓存头、`/classic/manifest.webmanifest`、`/classic/boot-theme.js` no-cache）、
  根 `/sw.js` = 退役脚本、`/api/v1/public/servers` 真实数据。

## 6. 修复与部署记录

### 6.1 v2.8.1（2026-10-12）：classic 挂载前缀全链路收口

**症状**：线上切换主题到 classic 白屏（`#app` 空），桌面/手机一致。

**根因链（v2.8 首发遗留，四处同源问题）**：

| # | 问题 | 后果 |
|---|---|---|
| 1 | classic 未设 Vite `base`，产物按根路径引用 `/assets/*` | 根作用域由 toy 的 dist 接管 → 404 → 模块不执行 → 白屏 |
| 2 | vue-router `createWebHistory()` 无 base | `/classic/` 下路由全不匹配，落到应用自带 404 视图 |
| 3 | boot 脚本内联在 index.html，被自身 CSP（`default-src 'self'`）拦截 | 偏好迁移与防闪屏**从未执行**，且只在控制台留 violation（静默失效） |
| 4 | `?theme=` 302 丢参数 | 偏好为旧值时，目标端 boot 按旧偏好把用户弹回原主题 |

**修复**：`web/vite.config.js` 加 `base: '/classic/'`；`web/src/router/index.js` 用
`createWebHistory(import.meta.env.BASE_URL)`；manifest 的 id/start_url/scope/icons 迁
`/classic/`；boot 逻辑外置为两主题各自的 `public/boot-theme.js`（后端按作用域提供、
no-cache、缺失 404）；`?theme=` 302 带参；boot 在 dev 端口跳过路径迁移。

**发版与部署**：

| 项 | 值 |
|---|---|
| 提交 | `50b79eb`（`fix(theme): v2.8.1——classic 挂载 /classic/ 全链路收口`） |
| 构建 | GitHub Actions run `38192579760` 成功，推送 `ghcr.io/yoahoug/beacontower:latest`，digest `sha256:2734b2adf7f9…`（2026-10-12T01:38:23Z） |
| 部署 | `/data/appdata/beacontower`：`docker compose pull && up -d`（容器重建 + `image prune -f` 回收 11.39MB） |

**线上验收**（10.66.66.66:8091）：`/` toy 真实数据渲染、点击主题中心 → `/classic/` 完整
控制台（`/classic/assets/*` 全 200）、classic 侧栏切回 toy、`/?theme=classic` 302 带参并
落到 classic、偏好 classic 时访问 `/` 自动迁移、`/classic/boot-theme.js` 200/no-cache、
根 `/sw.js` 仍为退役脚本。截图确认页脚 `v2.8.1 · SKY BEACON`。

**教训**：① 挂载前缀是三处契约（Vite base / 路由 base / manifest scope），少一处就是
「能打开但不对」；② CSP 下内联脚本是静默失效，前端引导逻辑一律走同源外部文件；
③ HTTP 直连（10.66.66.66:8091）非安全上下文，SW/PWA 只在反代域名（HTTPS）下生效。

### 6.2 v2.8.2（2026-10-12）：移动端抽屉层级 + 主题命名统一

**症状**：手机端（≤720px）打开左侧抽屉后，品牌区被吸顶顶栏压住、底部状态卡与「主题」
入口被底部 tab bar 压住——三者在同一 z 层（`--bt-z-sticky`=20），后渲染的护栏盖住抽屉；
遮罩仅 19，护栏不受遮罩管辖，点哪都像「抽屉被钉死」。

**修复**：

- 新增层级令牌 `--bt-z-drawer-mask: 30` / `--bt-z-drawer: 31`：抽屉高于顶栏与底部
  tab bar，遮罩夹在中间——打开抽屉时整页一起压暗，点遮罩任意处可关（原来护栏在遮罩
  之上，点顶栏/底栏区域关不掉）。
- 抽屉避让安全区（`env(safe-area-inset-top/bottom)`）：PWA 独立窗口下品牌区不再钻到
  状态栏底下、版本行不再贴 home indicator；顶栏吸顶位置同样避让刘海。
- 视口离开 ≤720px 断点（手机横屏/窗口放大）时自动收起抽屉，避免桌面留下无主遮罩。
- 主题命名统一：classic 主题显示名由「Classic Glass · 经典天空玻璃拟态」改为
  **「Sky Glass · 天空玻璃拟态」**，与页脚 codename（SKY BEACON）、README 称呼一致；
  内部 id 与挂载路径保持 `classic` / `/classic/`（localStorage 偏好值与已装 PWA
  的 start_url 是既有契约，不动）。

**验证**：390×844 视口下抽屉 z=31 > 遮罩 30 > 顶栏/底栏 20，品牌区 top=9 与抽屉 top=8
齐平、底部状态卡 bottom=823 在抽屉内（不再被 tab bar 的 775 压住）；桌面 1440×900
布局零回归（侧栏仍 sticky、tab bar `display:none`、无横向溢出）；主题中心显示
「🪟 Sky Glass · 天空玻璃拟态」。

### 6.3 v2.8.3（2026-10-12）：classic 壳更新链路自管（旧壳钉死）

**症状**：v2.8.1、v2.8.2 连发两版后，手机从主屏 PWA 启动仍是旧界面（白屏修复、抽屉修复
「看起来都没生效」），而同一域名在桌面浏览器已是新版。

**根因**：与挂载前缀无关，是**壳的新鲜度**问题，两层叠加——① classic 的 Workbox SW 用
generateSW 默认形态（`navigateFallback` + `createHandlerBoundToURL('index.html')`），
导航**只认预缓存**；② 旧版 `autoUpdate` 把 `skipWaiting()` 放脚本顶层，部分内核下「装了
不接管」。新 SW 停在 waiting 期间，用户就被预缓存里的旧壳钉死。

**修复**：SW 改 injectManifest 自管（`web/src/sw.js`）+ 页面侧更新治理
（`web/src/pwa.js`）：导航 NetworkFirst（1.5s 上限）、install 期 skipWaiting、activate 时
clientsClaim、`/api/**` 不进 SW；两个主题的 boot 脚本阻塞改 `defer`。完整根因分析与验收
见 doc/15 §8。

**Cloudflare 实测**（决定「发布多久生效」，须按三类资源分开看）：

| 路径 | 源站响应头 | 边缘行为 |
| --- | --- | --- |
| `/classic/`、`/`（HTML 壳） | `no-cache` | `cf-cache-status: DYNAMIC`——边缘**不缓存**、永远回源；这是 NetworkFirst 能立刻拿到新壳的前提 |
| `/classic/assets/*`（hash 名） | `immutable, max-age=31536000` | 边缘缓存；内容寻址下长缓存安全 |
| `/classic/sw.js`、`/classic/boot-theme.js`、`/sw.js` | 源站 `no-cache` | 被改写为 `max-age=14400`（CF「浏览器缓存 TTL」4h）：SW 脚本更新最多滞后 4h 到浏览器。壳不受影响（HTML 不缓存 + NetworkFirst），界面不会被它拖住 |

**教训**：① 「挂载前缀正确」与「发布能生效」是两件事，主题化项目必须分别验收；
② 缓存要按 HTML / hash 静态资源 / SW 脚本三类分别判断，语义完全不同；
③ 10.66.66.66:8091 是明文 HTTP、非安全上下文，SW 只在 HTTPS 域名下生效——线上 SW 的验收
必须在 `tower.yoahoug.dev` 上做。
