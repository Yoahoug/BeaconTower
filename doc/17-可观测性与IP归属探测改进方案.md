## 1. 问题一：「未定位」——IP 归属探测失效

### 1.1 现场证据（2026-10-11 只读采集）

**数据库**（`sqlite3 -readonly`）：

| server_id | name | region | region_source | profile.geo_country / geo_city |
|---|---|---|---|---|
| 1 | 本机 | 中国内地 | manual | 空 / 空 |
| 2 | 阿里云-My | 中国内地 | manual | CN / Chengdu |
| 3 | 阿里云-Z | 中国内地 | manual | CN / Chengdu |
| 4 | **Rack** | **未定位**（字面量） | **manual** | 空 / 空 |

**面板宿主出网对照**（Rack 公网 107.173.35.9）：

| 路径 | 结果 |
|---|---|
| `curl http://ip-api.com/json/...` 直连 | `Empty reply from server`（被重置/空回） |
| `curl -x http://127.0.0.1:7890 http://ip-api.com/...`（经 mihomo） | **502 Bad Gateway**（同代理访问 Google=302、DB-IP 下载=200，代理本身健康） |
| `https://ip-api.com/...` | 不可用（免费版接口只支持 HTTP，代码硬编码的就是 https） |
| 离线 mmdb | `find /data/appdata/beacontower -name '*.mmdb'` **无文件**；compose 未设 `BEACON_GEOIP_*`、未设 `BEACON_PROXY_URL` |

**展示位置**：公开监控页节点卡片 `web/src/components/monitor/NodeCard.vue:100` 的 `{{ server.region }} · {{ profile.os }} · {{ profile.arch }}`，region 来自 `web/src/stores/monitor.js:70`（空值回退 `'未定位'`）。Rack 的 region **字段本身就是「未定位」**，不是显示层的兜底。

### 1.2 根因链（代码定位）

1. `internal/geoip/geoip.go:239` `Lookup` 解析链 = 内网直返 → 离线 mmdb → 在线回显 → 静态映射 → **兜底返回 `&Result{Region:"未定位"}`，永不返回 nil**（:266）。调用方无法区分「解析失败」与「解析成功但无中文名」。
2. `internal/handler/servers.go:259-269`（CreateServer）：`region` 为空时 `if r := geoip.Lookup(ip); r != nil { region = geoip.RegionText(r) }` —— 兜底文案被当作 region **落库**（本应留空 + 保持 auto）。
3. 前端编辑保存会把已存的「未定位」原样回传（`ServerEditorModal.vue:62` 预填 `props.server.region`、`:212` 提交）→ `UpdateServer` 里非空值一律记 **manual**（`servers.go:346-352`）→ 采集侧自愈（`collector.go:313` 仅 `region_source=='auto'` 时 `UpdateRegion`）**被永久关闭**；「重定位」按钮对 manual 节点也是空操作（`servers.go:585` 同判断）。
4. 在线回显在当前部署形态本就不可用：硬编码 `https://ip-api.com`（`geoip.go:189`，免费源不支持 HTTPS）+ 未配 `BEACON_PROXY_URL`（宿主直连外网被墙）+ 代理对 ip-api 返回 502。
5. 无离线库兜底：镜像/数据目录均无 `geolite2-city.mmdb`（`main.go:83` `geoip.Init(cfg.DataDir)`，容器内即 `/app/data/geolite2-city.mmdb`）。
6. 附带：`profile.geo_country/geo_city` 只在**公网 IP 变化时**刷新（`collector.go:311-317`），阿里云两台的 CN/Chengdu 是链路早期可用时的历史值；本机/Rack 为空——**即使换好解析源，存量行也需要一次「重定位/数据修复」才会回填**。

### 1.3 修复方案

#### A. 运维级即修（不改代码，建议立即执行）

代码本来就是「离线库优先」，把免费 **DB-IP Lite City**（MaxMind mmdb 格式，与 `geoip2-golang` 兼容）放到数据目录即生效：

```bash
cd /data/appdata/beacontower/data
curl -x http://127.0.0.1:7890 -fL -o dbip-city-lite.mmdb.gz \
  'https://download.db-ip.com/free/dbip-city-lite-2026-10.mmdb.gz'   # 已验证 200，约 60MB
gunzip -k dbip-city-lite.mmdb.gz && mv dbip-city-lite.mmdb geolite2-city.mmdb
docker compose -f /data/appdata/beacontower/docker-compose.yml restart beacontower
docker logs --since 2m beacontower 2>&1 | grep geoip   # 期望：[geoip] city db loaded: /app/data/geolite2-city.mmdb
```

- 然后 UI 修复存量：清空 Rack 的「地区」输入并保存（`servers.go:349-351` 空值 → 复位 auto）→ 点「重定位」→ region 回填为「美国」；本机同理。
- **授权注记**：DB-IP Lite 为 CC BY 4.0，需在 README/关于页署名 “IP Geolocation by DB-IP (https://db-ip.com)”；文件按月更新（文件名带月份）。
- 验收：公开页 Rack 卡片显示「美国 · Ubuntu 24.04 · x86_64」；`server_profile.geo_country='US'`。

#### B. 代码级（下一小迭代，风险低）

1. `geoip.Lookup` 失败返回 `nil`（或新增 `Resolved()` 判定），`RegionText` 不再向存储层输出「未定位」；
2. `CreateServer`/`UpdateServer` 增加守卫：region 值为空 **或等于占位文案** → 视为自动（source=auto）并留空，杜绝占位文案落库（防复发，兼顾前端未改造期）；
3. 在线回显换 `http://ip-api.com` + 多源回退（ipinfo / ip.sb 等），统一走 `BEACON_PROXY_URL`；compose 增补该 env 的注释说明（可选，离线库到位后它只是兜底）；
4. （可选）构建期把 mmdb 打进镜像或由部署脚本拉取，避免手工文件随容器丢失。

#### C. 数据修复

Rack `region_source` 复位 `auto`（优先用 UI 清空重存，保留操作审计）；`profile.geo_*` 如需立即回填，可触发一次「重定位」后等下一轮采集，或做一次性数据修复脚本（低优先，展示上以 region 为准）。

### 1.4 影响面与边界

- 只影响展示与回显（region / geo_country / geo_city），不参与组网与采集决策；公开链路依旧只见地区文案不见 IP（doc/05 §5 不破）。
- **前端边界**：公开页/详情页的展示逻辑（`NodeCard.vue`、`ServerDetailView.vue`、`monitor.js`）无需改动；`ServerEditorModal`/`ServersView` 的预填与守卫属前端重构范围，**待重构合并后再做**（当前前端有未提交改动，勿并行修改）。

## 2. 问题二：WG 任务执行中无可观测日志

### 2.1 现状（以任务 #12「配置备援中心 · Rack」为例）

- 步骤执行中**空日志**：`StartWGTaskStep` 只写状态与开始时间（`internal/store/wg.go:363`），日志在 `FinishWGTaskStep` 完成时一次性落一行（`:369`）。
- 成功路径几乎无进程日志：`task.go` 仅失败/异常分支有 `log.Printf`（:138 解密失败 / :163 panic / :206 hub 步骤失败 / :237 spoke 步骤失败 / :290 任务结束 / :352 ufw 非阻断失败）。
- 实测结论重复拼两遍：任务 #12 步骤日志为同一句「UDP 51820 面板侧握手成功（1.173s…）」×2。
- 探测值语义不可辨：`ProbeUDP` 的 RTT 是「自首包发出起的累计值，任一次尝试的回应都接受」（`probe_udp.go:238/255`，3 次尝试间隔 `timeout/6`）。1.173s 究竟是「真 RTT 1.17s」还是「第 3 次尝试才成功」无法从日志分辨（对照：国内中心同探测为 16-23ms）。

### 2.2 方案（按优先级）

| 优先级 | 改动 | 落点 |
|---|---|---|
| **P0-1** | 步骤**分阶段增量日志**：新增 `AppendWGTaskStepLog`，`applyHubNode`/`applySpoke` 各阶段各写一行（预检结论 / 装包 / UDP 放行 / 配置渲染字节数与端点 / 写盘 600 / 启动 / `wg dump` 自检 / 端点解析 / 实测结论），每行带相对耗时 `+Δms` | `store/wg.go`、`wg/task.go` |
| **P0-2** | 成功路径 `log.Printf`：任务开始（中心/成员/角色清单）、单节点开始与完成（耗时）、任务收尾（成功/失败/跳过与总耗时） | `wg/task.go`（:290 已有收尾，补齐前后） |
| **P1-3** | 探测明细与去重：写「第 N 次尝试成功 · 单次 RTT x ms」（`ProbeUDPResult.Attempt` 已存在，扩一个单次耗时字段即可），note 只保留最后一次结论 | `wg/probe_udp.go`、`probe_hub.go:260-281`、`task.go` 阶段 2.5 |
| **P1-4** | 超时预算与耗时可见：步骤日志开头写明预算（hub 120s / spoke 90s，`task.go:64-65`），结束写实际耗时 | `wg/task.go` |
| **P2-5** | 面板动作进容器日志：provision / reissue / register / switch 等 handler 各加一行 `log.Printf`（现仅进审计表，`docker logs` 看不到） | `handler/wg_provision.go`、`wg_hub.go` |
| **P2-6** | 前端（**待协调**）：任务弹窗「进行中」状态与子步骤耗时展示——属 MeshView/任务弹窗范围，需与前端重构合并后排期 | web（另行协调） |

### 2.3 验收

- 任务执行中刷新即可见 ≥5 行过程日志，失败时最后一行给出**具体阶段**与错误；
- 成功日志含每步耗时与 UDP 探测「尝试次数 + 单次 RTT」；
- `docker logs` 能看到每次面板动作的一行记录。

## 3. 附录 A：Rack 作中继的延迟实测（只读，未切换线上状态）

**方法**：ICMP（50/20 包）、`mtr`、隧道内 ping、历史任务步骤日志对照。**未执行任何 `wg set` / 切换中心 / takeover / 配置改写**；线上现役中心仍为阿里云-My（server_id=2）。

### 3.1 数据（2026-10-11 18:51–18:55）

| 观测点 → 目标 | 方法 | 结果 |
|---|---|---|
| 面板宿主 → Rack `107.173.35.9` | ICMP ×50 | **min/avg/max = 227.3 / 228.1 / 230.9 ms**，0% 丢失，mdev 0.67ms |
| 面板宿主 → Rack | `mtr -rwzc 8` | 直达 AS36352（RackNerd/ColoCrossing），Avg 233.4ms，0% 丢失 |
| Win PC(10.66.66.10) → Rack | ICMP ×20 | avg 225ms，0% 丢失 |
| 面板宿主 → 阿里云-My / 阿里云-Z | ICMP | 100% 丢失（安全组未放行 ICMP；WG 隧道正常，属策略性丢 ICMP） |
| 面板宿主 ↔ Win PC（**经现役中心**中转） | `ping 10.66.66.10` / `ping 10.66.66.66` | **24–26ms 往返**（单腿 ≈12–13ms） |
| 历史任务步骤：国内中心 UDP 真握手 | 面板侧实测 | **16–23ms**（UDP 51830，多次记录） |
| 历史任务步骤：Rack UDP 真握手 | 面板侧实测 | **1.173s / 1.402s**（任务 #12，两次均如此） |

### 3.2 读数与推演

- 「1.173s」是 `ProbeUDP` 自**首包发出起**的累计计时、任一次尝试成功都算（`probe_udp.go:255`）。按 3 次尝试/2–2.5s 预算推算，该值意味着**第 2–3 次尝试才拿到回应**，即该方向 UDP 存在丢包/慢回——与国内中心 16-23ms 的干净路径形成鲜明对照。
- 面板宿主上 `ip route get 107.173.35.9` → **经本机 SakuraiTunnel（198.18.0.2，table 2022）**；国内中心 IP 同样进该 TUN（代理内规则对国内走直连，故仍是 12ms 级）。即 **228ms 已包含本机代理链路的代价**，未代理路径可能略低，但量级不变。
- **Rack 作中继的成员互访 RTT**：
  - 乐观口径（ICMP 单腿 228ms）：≈ **0.46s**；
  - 按 UDP 实测口径（含重传/尝试，单腿 0.3–0.6s+）：≈ **0.6–1.2s**。
  - 对照现役中心 ≈ **25ms**：**劣化 20–40 倍**。
- **结论**：Rack 作中心只适合「夜间批量同步/备份」类流量轮换；**不适合交互**（SSH/RDP/网页）。若确要启用：先在代理规则中为 `107.173.35.9:51820` 加直连（bypass）再复测 UDP；切换走既有金丝雀门槛（切换前 UDP 实测 + 失败即回滚），并做一次真隧道长测（连续 keepalive 丢包率）。
